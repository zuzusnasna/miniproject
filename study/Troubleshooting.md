# 🎮 GAMEHUB Troubleshooting

게임 커뮤니티 프로젝트를 구현하면서 실제 개발 및 배포 과정에서 발생했던 문제와 해결 과정을 정리한 문서입니다.

> 프로젝트: Java Servlet 기반 게임 커뮤니티
> 
> 기술: Java · Jakarta Servlet · Maven · Tomcat · Oracle · HTML/CSS/JavaScript

---

## 1. Oracle 접속 과정에서 SID와 Service Name 혼동

### 문제

Oracle DB 연결 과정에서 접속 정보가 맞지 않아 애플리케이션에서 DB 연결이 정상적으로 이루어지지 않았습니다. 특히 `XEPDB1`을 SID처럼 사용하거나 Service Name과 SID를 혼동하면서 접속 오류가 발생했습니다.

### 원인

Oracle XE 환경에서는 SID와 Service Name의 개념이 다르며, 사용하는 JDBC URL 형식에 따라 접속 대상이 달라집니다.

### 해결

JDBC 연결 정보를 실제 Oracle 서비스 구성에 맞게 확인하고, 프로젝트에서 사용하는 DB 계정과 Service Name을 일치시켰습니다.

### 배운 점

DB 연결 오류가 발생했을 때 단순히 URL만 수정하기보다 **Oracle Listener → Service Name/SID → 계정 → JDBC URL** 순서로 확인하는 것이 중요하다는 것을 배웠습니다.

## 2. Tomcat 실행 후 404 오류 발생

### 문제

IntelliJ에서 Tomcat을 실행했지만 `/`, 애플리케이션 Context Path, 게시판 페이지 등에 접근했을 때 `404 Not Found`가 발생했습니다.

### 원인

WAR 프로젝트에서는 서버가 실행되는 것과 웹 애플리케이션이 정상적으로 배포되는 것은 별개의 문제입니다. Artifact가 Tomcat에 배포되지 않았거나 Context Path가 실제 배포 경로와 일치하지 않는 경우 404가 발생할 수 있습니다.

### 해결

IntelliJ의 Tomcat Run/Debug Configuration에서 Deployment 항목을 확인하고 `war exploded` Artifact가 실제로 배포되는지 확인했습니다. 이후 실제 Context Path를 기준으로 URL을 확인했습니다.

### 배운 점

`Tomcat이 실행된다 = 웹 애플리케이션이 정상 실행된다`가 아니라는 점을 이해했습니다. 서버 실행 상태와 **Artifact 배포 상태, Context Path, 실제 요청 URL**을 각각 확인해야 합니다.

## 3. 애플리케이션 Context Path 변경에 따른 경로 문제

### 문제

개발 과정에서 애플리케이션 경로가 기존 `gamecommunity_`에서 `gamecommunity1`로 변경되면서 HTML, JavaScript, 이미지 등의 일부 경로가 기존 Context Path를 참조하는 문제가 발생했습니다.

### 원인

정적 리소스와 요청 URL에 애플리케이션 Context Path가 직접 포함되어 있거나 이전 배포 경로가 남아 있었습니다.

### 해결

애플리케이션에서 사용되는 요청 경로를 현재 배포 Context Path 기준으로 확인하고, 특히 정적 리소스와 Fetch 요청 경로를 점검했습니다.

### 배운 점

웹 애플리케이션의 경로는 단순한 URL 문자열이 아니라 **배포 환경과 연결되는 설정**이므로 Context Path를 변경할 때 관련 리소스 경로를 함께 점검해야 합니다.

## 4. 로그인 세션 Attribute 이름 불일치

### 문제

로그인 성공 후 세션에 회원 정보를 저장했지만 게시글 상세/삭제 기능에서 로그인 사용자를 정상적으로 인식하지 못하는 문제가 발생했습니다.

### 원인

로그인 처리에서는 세션에 회원 정보를 `"member"`라는 이름으로 저장하고 있었지만, 일부 게시글 관련 Servlet에서는 `"loginMember"`를 조회하는 등 세션 Attribute 이름이 일치하지 않았습니다.

### 해결

로그인 시 저장하는 세션 Attribute와 각 Servlet에서 조회하는 Attribute 이름을 동일하게 맞추도록 확인했습니다.

```java
session.setAttribute("member", member);
```

이후 다른 Servlet에서도 동일한 세션 Attribute를 기준으로 로그인 회원 정보를 가져오도록 수정했습니다.

### 배운 점

세션 기반 로그인에서는 **세션 Attribute 이름 자체가 기능 간 연결 규칙**이 됩니다. 로그인, 회원 정보, 게시글 권한 검사를 구현할 때 동일한 이름을 사용하는 것이 중요하다는 것을 배웠습니다.

## 5. 게시글 삭제 권한과 로그인 사용자 정보 연결

### 문제

게시글 삭제 기능에서 작성자 여부만 확인하는 것에서 나아가 시스템 관리자와 카테고리 관리자의 권한까지 구분해야 했습니다. 하지만 로그인 사용자 정보와 권한 정보를 정확하게 연결하지 않으면 삭제 버튼이 표시되지 않거나 삭제 요청이 거부되는 문제가 발생했습니다.

### 원인

게시글 작성자와 관리자 권한은 서로 다른 기준으로 판단해야 합니다.

- 일반 사용자: 본인이 작성한 게시글만 삭제
- `CATEGORY_MANAGER`: 담당 카테고리의 게시글 삭제
- `SYS_MANAGER`: 전체 게시글 삭제

따라서 단순히 게시글 작성자 여부만으로 삭제 권한을 판단하면 관리자 기능을 처리할 수 없습니다.

### 해결

게시글의 작성자 정보와 현재 로그인 회원의 역할(Role), 그리고 게시글의 카테고리를 함께 확인하는 방식으로 권한 구조를 분리했습니다.

### 배운 점

권한 기능은 단순히 `isWriter` 하나로 처리하는 것이 아니라 **사용자 → 역할 → 대상 리소스 → 허용 작업**의 관계를 기준으로 설계해야 한다는 것을 배웠습니다.

## 6. 카테고리 관리자 권한 범위 문제

### 문제

`CATEGORY_MANAGER`는 모든 게시글을 삭제할 수 있는 것이 아니라 자신이 관리하는 카테고리에서만 관리 기능을 수행해야 했습니다.

### 원인

역할(Role)만 확인하면 어떤 카테고리를 관리하는지 알 수 없습니다. 카테고리 관리자와 카테고리의 연결 정보가 추가로 필요합니다.

### 해결

게시글의 `CATEGORY_ID`와 관리자가 담당하는 카테고리를 비교하여 권한 범위를 제한하는 구조로 처리했습니다.

### 배운 점

실제 서비스의 권한은 **Role 기반 권한 + 리소스 범위 기반 권한**이 함께 필요할 수 있다는 것을 경험했습니다.

## 7. 기존 이미지 경로와 현재 애플리케이션 경로 불일치

### 문제

DB에 저장된 카테고리 아이콘 URL에 이전 Context Path인 `/gamecommunity_/images/icon/...`가 남아 있었지만 현재 애플리케이션은 `/gamecommunity1` 경로로 배포하려고 했습니다.

### 원인

DB에 저장된 URL이 애플리케이션의 현재 배포 경로와 결합되어 있었습니다. Context Path가 변경되면 DB에 저장된 절대 경로가 더 이상 현재 애플리케이션과 맞지 않을 수 있습니다.

### 해결

DB 데이터를 일괄 수정하기보다 애플리케이션에서 기존 경로를 현재 Context Path에 맞게 처리하는 방향으로 수정했습니다.

### 배운 점

DB에 저장하는 URL에 애플리케이션의 Context Path를 직접 포함시키면 배포 경로 변경 시 유지보수가 어려워질 수 있습니다. 정적 리소스 경로와 배포 경로를 분리하는 설계가 중요하다는 것을 배웠습니다.

## 8. `war exploded` Artifact 배포 문제

### 문제

Tomcat은 정상적으로 시작되었지만 웹 애플리케이션이 접근되지 않거나 Artifact가 배포되지 않았다는 메시지가 나타났습니다.

### 원인

IntelliJ의 Tomcat 설정에서 배포 대상 Artifact가 누락되거나 잘못 설정된 경우 서버는 정상 실행되어도 애플리케이션은 배포되지 않을 수 있습니다.

### 해결

Tomcat 설정의 Deployment 항목에서 프로젝트의 `war exploded` Artifact가 등록되어 있는지 확인하고, Artifact의 Output Directory와 Application Context를 함께 점검했습니다.

### 배운 점

WAR 프로젝트를 실행할 때는 다음 세 가지를 함께 확인해야 한다는 것을 배웠습니다.

1. Tomcat 서버 실행
2. Artifact 생성 및 배포
3. Application Context Path 확인

## 9. 문제 해결 과정에서 확인 순서 정립

처음에는 오류가 발생하면 코드를 바로 수정하려고 했지만, 프로젝트를 진행하면서 환경 문제와 코드 문제를 먼저 구분하는 것이 중요하다는 것을 알게 되었습니다.

### 확인 순서

```text
브라우저 요청
   ↓
HTTP 상태 코드 확인
   ↓
Tomcat 로그 확인
   ↓
Servlet 요청 매핑 확인
   ↓
Session / Parameter 확인
   ↓
DAO 및 SQL 확인
   ↓
Oracle 연결 상태 확인
```

특히 `404`, `500`, DB 연결 오류를 같은 방식으로 접근하지 않고 **발생 위치를 먼저 좁힌 뒤 수정**하는 방식으로 문제 해결 방법을 개선했습니다.

## 10. 프로젝트를 통해 얻은 Troubleshooting 경험

GAMEHUB를 개발하면서 단순히 기능을 구현하는 것뿐만 아니라 실제 웹 애플리케이션에서 발생하는 환경 설정, 배포, 세션, 권한, DB 연결, 경로 문제를 직접 경험했습니다.

특히 다음과 같은 문제 해결 경험을 얻었습니다.

- Oracle JDBC 연결 및 Service Name 확인
- Tomcat WAR 배포 과정 이해
- IntelliJ Artifact 및 Context Path 관리
- Session 기반 로그인 상태 관리
- Role 기반 게시글 권한 설계
- 카테고리 범위 기반 관리자 권한 처리
- Context Path 변경에 따른 정적 리소스 문제 해결
- DB와 애플리케이션 사이의 데이터/경로 의존성 점검

이 경험을 통해 오류 메시지만 보고 코드를 수정하기보다 **문제가 발생한 계층을 먼저 파악하고 원인을 단계적으로 좁혀가는 방식**으로 문제를 해결하는 습관을 만들었습니다.
